## 稀疏检索（Sparse Retrieval）

- 传统关键词思路：BM25 / TF-IDF
- 向量形态
- 几万维，绝大多数是 0
- 高维，少数非零
- 本质：数词频——"快递"这个词在文档里出现了几次
- 侧重关键词检索

## 稠密检索（Dense Retrieval）

- 语义向量思路：Embedding 模型
- 向量形态
- 几百~两千维，全是数值
- 本质：理解语义——把文本映射到一个"语义空间"，意思相近的文本，向量距离就近
- 侧重语义检索

## Reranker（重排序）

- 计算 query 与文档之间的相关性得分
- 注意：是**语义**的相关性，而不是关键词的相关性


## 分块大小为什么不宜太长

- 父文档不宜太长
- 原因：模型上下文长度有限，只支持这么多词元

## BGE-M3 与 BGE-Reranker-Large 对比

![20260823_222318](screenshots/20260823_222318.jpg)

| 对比维度 | BGE-M3 | BGE-Reranker-Large |
| --- | --- | --- |
| 主要用途 | 召回 / 向量化 | 精排 / 评分 |
| 文本长度支持 | ≈ 8192 tokens | ≈ 512 tokens（典型） |
| 多语种能力 | 强（100+ 语言） | 中等（支撑中英） |
| 优势 | 快速召回，高效检索 | 高精度排序 |

## 为什么要存 file_path（文档路径）

- 因为知识库
- 它一定涉及到知识的增删改查
- 例如
- 法律条文变化了
- 因此
- 需要找到知识库的那个知识的位置
- 删除
- 更新
- 重新解析
- 进行知识的管理
- 以文档路径作为 `file_path`
- 不像 MySQL 一样逻辑删除
- 就直接物理删除了
- 因为旧版本的只要在
- 就影响解析
