## Few-shot vs Zero-shot
| 维度 | Zero-shot (零样本) | Few-shot (少样本) |
| :--- | :--- | :--- |
| 示例数量 | 0 个 | 1 个或多个 (通常 2-5 个) |
| 核心逻辑 | 考验模型的通用理解能力 | 考验模型的模仿和学习能力 |
| 输出稳定性 | 较低（容易发散） | 较高（格式和风格更可控） |
| Token 消耗 | 低 | 较高（示例会占用上下文窗口） |
| 最佳用途 | 翻译、简单问答、常识推理 | 情感分析、特定格式转换、复杂分类、风格模仿 |

- 一句话建议：
- 如果你发现 Zero-shot 的效果不好，或者模型总是搞错格式， 
- 立刻切换到 Few-shot，通常能立竿见影地解决问题。

## 稀疏检索（Sparse Retrieval）

- 传统关键词思路：BM25 / TF-IDF
- 向量形态
- 几万维，绝大多数是 0
- 高维，少数非零
- 本质：数词频——"快递"这个词在文档里出现了几次
- 侧重关键词检索

## 稠密检索（Dense Retrieval）

- 语义向量思路：Embedding 模型
- 向量形态
- 几百~两千维，全是数值
- 本质：理解语义——把文本映射到一个"语义空间"，意思相近的文本，向量距离就近
- 侧重语义检索

## bert vs 大模型
- bert优点：没有幻觉，不会像大模型一样，“不在你指定的两个分类，出现新的分类”
- bert优点：推理性能容易优化，容易提高并发量，大模型并发有限制、会成为瓶颈
- bert缺点：只能处理短文本
- bert缺点：很难根据多轮对话识别当前意图

# 举个例子
##  用户提问：“公司报销差旅费的标准是多少？” 
- 知识库里的原文（正确答案）：“员工出差住宿标准为一线城市每晚 500 元，二线城市 300 元。餐饮补贴每天 100 元。”


# 衡量指标1/4：上下文相关性(怕多，检索回来的内容，跟问题是否沾边，不要废话，公式：question/context)
- 通俗解释：检索回来的内容，跟问题沾边吗？
- 好例子：检索到了上面那段关于"住宿和餐饮补贴"的文字。-> 相关
- 坏例子：检索回来一段"公司食堂午餐菜单"或者"2018年的旧版报销制度"。-> 不相关
- 惩罚冗余信息。
- 从上下文抽取对回答问题有用的句子s，上下文句子总数q。
- 8个句子有用，2个对回答这个问题不相关。 8/10
- Directly go to her for help, not anyone else.
![20260824_130547.jpg](screenshots/20260824_130547.jpg)

# 衡量指标2/4：上下文召回率（怕少，召回的东西，完整不完整，全不全，别丢三落四，公式：ground truth/context）
- 通俗解释：关键信息找全了吗？有没有漏掉？
- 好例子：把"一线城市500、二线300、餐饮100"全找回来了。-> 召回率高
- 坏例子：只找回了"一线城市500"，漏掉了"餐饮补贴100元"这一条。-> 召回率低
- ground truth里的声明，有x%被召回了。
- Have I got all of you? Am I missing anything? I need all your pieces.
![20260824_131031.jpg](screenshots/20260824_131031.jpg)

# 衡量指标3/4：忠实度（评估模型幻觉，是不是自己加东西进去了，夹带私货程度，给自己加了戏，公式：context里出现的answer的陈述句的数量/answer）
- 通俗解释：模型是不是在"瞎编"？答案是否完全基于检索到的内容？
- 好例子：模型回答："一线500，二线300，餐补100。"（完全照搬原文事实）。-> 忠实
- 坏例子：原文没说交通费和打车费，模型却自己加戏说："此外，打车费实报实销。"（这是模型自己脑补的，原文没写）。-> 不忠实（幻觉）
- How faithful are those answers? Are they making up stories? Are they fabricating?
![20260824_131721.jpg](screenshots/20260824_131721.jpg)

# 衡量指标4/4：答案的相关性（根据answer生成潜在问题q2，把q2向量化，把query向量化，计算q2与query的cosin余弦相似度的average）
- 通俗解释：最终生成的回答，直接解决用户问题了吗？
- 好例子：直接列出金额标准。-> 相关
- 坏例子：回答了一大堆"报销流程很复杂，需要填表，找领导签字……"，但就是没提具体是多少钱。虽然话没错，但没回答核心问题。-> 不相关
- 潜台词：别答非所问，直接给结果。
- Questions and answers should always be in the 'exactly' same direction.

## topK（召回数量）如何选择
- 1. 子问题分解：topK 至少大于子问题数量
- 2. 评估指标：检索的精确率和召回率 
  - 选择一定量的 query 测试
  - topK 小 → 召回率低、精确率高
  - topK 大 → 召回率高、精确率低（milvus混合检索出来了很多不相关的问题， reranker也懵了）

## 高频问答对，不用bm25
- 高频问答对数据特点： 量少， 不会经常变。
- 可以改用bge-m3模型，将高频问答数据进行稠密向量编码，存储到内存或者milvus向量数据库中。
- 为什么单独存到一个向量数据库中，因为数据量少且不变，不需要去巨大的知识库海里捞针，直接在小的“高频库”里秒级返回结果。架构解耦：把“高频标准问”和“长尾复杂问”分开处理，是构建企业级 RAG 系统的最佳实践。
- bm25是基于字面匹配的。它只认关键词，不懂语义。
